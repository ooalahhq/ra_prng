# Fairness audit — 2026-11-04 PRNG shootout and Monte Carlo

## Measurement contract

The measured comparison has three separate regimes: scalar sequential generation (Suites A, B and D), eight independent AVX2 streams (Suite C), and complete Monte Carlo consumers. The compiler disables automatic tree vectorization for all four binaries while retaining explicit AVX2 intrinsics. Floating point contraction is disabled so scalar and AVX2 π consumers can use the same top-24-bit midpoint conversion. The run command pins each program to one allowed CPU core and records the compiler, flags, source dependencies, binary and output hashes in `data/fairness_manifest.json`.

`python3 run_fairness.py` compiles and runs each program sequentially. `python3 run_fairness.py --audit-only` checks existing output. Every microbenchmark row has one warmup and seven timed samples in `data/shootout_samples.csv`; every Monte Carlo timing row has five raw samples in its workload JSON. The audit recomputes minimum and median timings, and checks microbenchmark MiB/s and cycles per byte against the actual output byte count. `data/shootout_sample_summary.json` contains both minimum and median throughput for all microbenchmark rows.

## Validity gates

| Gate | Evidence | Interpretation |
| --- | --- | --- |
| Baseline correctness and implementation parity | `[KAT GATE]` in `shootout_microbench.log` | Known-answer checks and same-generator scalar/AVX2/engine parity pass before timed microbenchmarks. |
| Photon RA stream parity | `[PHOTON STREAM PARITY]` in `mc_workload1.log` | OTF and eager RA implementations produce identical words for tested keys and burst lengths; natural stochastic trajectories are still allowed to differ across families. |
| π consumer parity | `[PI CONSUMER PARITY]` in `mc_workload2.log` | Shared generators produce identical inside counts in scalar and AVX2 consumers for the tested K values. |
| Sample accounting | `data/fairness_manifest.json` | The audited minimum/median must agree with all saved raw samples. |
| Output work | Workload JSON and `RESULTS.md` | Native 64-bit inlined generators count 8 output bytes; odd-K π bursts record both generated and consumed words; photon reports draw counts. |
| Same-work tree comparison | `data/mc_workloads_v2.json` | RA schedules share node/output results. Philox has a different number of nodes and draws, so no cross-family tree speed ratio is reported. |

## Reading the results

- Suite A is *shootout-inspired*. It is not an exact replication of Vigna's harness or loop-unrolling policy.
- Suite A's native 64-bit continuous inlined endpoint and 32-bit direct-buffer endpoint have different call/output contracts; the inlined K=1 endpoint also returns 32-bit values. Figure 2 labels its `ns/word` values as costs per 32-bit-equivalent output. Figure 4's cross-family scatter compares the same AVX2 K=1 and K=15 regimes for every point.
- The AVX2 Suite C measures eight streams together. Its throughput is a different endpoint from scalar Suites A/B/D; no scalar/AVX2 ranking should erase that distinction.
- Photon total runtime includes trajectory-dependent work. Reported draw counts should accompany timing when different generator families are compared.
- Monte Carlo π uses equal coordinate conversion and consumer logic, but each family has its own random stream. `MiB/s` counts generated bytes, including the unused final word in odd-K bursts.
- The eight-lane flip diagnostic counts threshold-triggered Bernoulli flips; it has no Ising lattice or Metropolis acceptance rule. The source filename retains the historical `ising` spelling only.
- GBM generation and complete option-pricing time are reported separately. The generators' native seed/path mappings yield statistical payoff comparisons, not bit-identical trajectories.
- The statistical-quality and feature matrix is a manually curated synthesis in `build_dashboard_and_plots.py`, drawing on earlier experiments and reference claims. This speed run does not repeat or independently verify PractRand, NIST, Dieharder, SAC/BIC or other quality batteries. Treat those cells as contextual claims, not results of this benchmark.
- Minimum timings are descriptive best cases. The report counts rows whose median exceeds the minimum by more than 10%; use the raw medians to judge small performance differences. The run pins a core but does not lock CPU frequency or eliminate unrelated host activity.

`RESULTS.md` and `shootout_dashboard.html` are generated from the current JSON. `RESULTS_PRE_AUDIT.md` preserves the original narrative as historical material and is superseded for speed claims.

## Outcome of this run

The final audit reconciled 343 microbenchmark rows (2,401 timed samples) and 159 Monte Carlo timing rows (795 timed samples). No microbenchmark minimum was shorter than 5 ms. KAT, photon stream parity, and π consumer parity gates passed. However, 221 of 343 microbenchmark rows have a median time more than 10% above the minimum. The current numbers are suitable for describing implementation regimes and broad performance differences, while tight rankings and precise speedup factors require a lower-variance rerun on a quieter host. The dashboard and report surface this variability rather than treating minimum timings as precise estimates.
